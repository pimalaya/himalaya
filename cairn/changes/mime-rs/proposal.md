# Read and write mail with mime-rs

## Why

Himalaya parses with mail-parser and composes with mail-builder, and works around both: header values are re-read from the raw bytes (8-bit bytes, split encoded words), file names re-parsed, a text part's bytes re-decoded from its byte range because mail-parser transcodes it, a Message-ID generated by hand so mail-builder does not put the hostname in it. mime-rs (github.com/pimalaya/mime-rs) is Pimalaya's own MIME library, replacing both across the apps: a byte-faithful tree, JMAP's body lists, typed field readers and a strict builder.

## What

- **mime-rs pinned by git rev** (`d7ea032`) until its first release, which waits on its SIMD codecs being published; mail-parser and mail-builder removed.
- **One walk over the tree** (src/shared/message/part.rs) keeps the part ids a caller holds: the 1-based depth-first position over the message's parts, containers counted, an attached message one part; the IMAP sections and the `message-too-complex` bounds stay as they are.
- **Himalaya keeps its own reading policy where mime-rs reads otherwise**: raw 8-bit header bytes as UTF-8 else Windows-1252, a US-ASCII body that is valid UTF-8 read as UTF-8, the read view's address lists with their invalid entries. It reads them off mime-rs's raw field bytes rather than mail-parser's offsets.
- **The composer writes what mail-builder added implicitly**: `Date` (now, the local offset) and `Message-ID` (on the sender's domain).
- **No `--json` shape changes**; a difference in what a field holds is a regression unless the change says why.

## Verification

Every existing test passes unchanged, except where it pinned a mail-parser quirk, which the log names. `message parse --json` over mime-rs's corpus (tests/corpus, 153 messages) is compared before and after, each difference reviewed.
