# Read and write mail with mime-rs

mail-parser and mail-builder are gone from himalaya's code, replaced by mime-rs (github.com/pimalaya/mime-rs), pinned at `d7ea032` by git revision until its first release. mail-parser stays in the dependency tree only through io-pimdir; io-maildir's `parser` feature, which handed back mail-parser messages, is no longer enabled.

src/shared/message/part.rs is the one walk over the mime-rs tree. It keeps the part ids a caller holds (the 1-based depth-first position over the parts, containers counted, an attached message one part), the IMAP sections and the `message-too-complex` bounds, measured into attached messages, encoded ones included. Himalaya keeps its own reading where mime-rs reads otherwise, off the raw field bytes mime-rs keeps:
- raw 8-bit header bytes as UTF-8, else Windows-1252;
- adjacent encoded words joined as bytes;
- a US-ASCII-labelled body as UTF-8, else Windows-1252, mime-rs counting US-ASCII as UTF-8;
- an invalid `Content-Type` judged on the whole raw value, mime-rs stopping at the first byte past a token.

One `envelope::from_raw` serves Maildir, m2dir and mbox, and `address::from_mime` serves those three and the search evaluator, each of which had carried a copy of the mail-parser conversion.

The composer writes the `Date` and `Message-ID` mail-builder used to add. The id goes on the sender's domain, else the hostname (`gethostname`, which mail-builder already brought in), else `localhost`. A reply to an HTML-only message quotes its text through a small HTML-to-text step in part.rs, as mail-parser's `body_text` did.

What moved:
- `text` unwraps `format=flowed` (RFC 3676), the US-ASCII branch included.
- The plain view now reads its sizes, names and types the way the JSON does.
- Composed charset names are lowercase, so a test that pinned mail-builder's `UTF-8''` now compares without case.
- UTF-7 is no longer decoded. encoding_rs implements the WHATWG charsets, which leave it out; this is mime-rs divergence D3.

Corpus comparison: `message parse` was run over mime-rs's 153 corpus messages (dovecot, stalwart), before and after, in JSON and plain. 35 JSON views differ, all from malformed or synthetic mail, each reviewed:
- **Structure:** an outer delimiter closing a nested multipart now splits three attached messages that mail-parser read as one (dovecot-thirdparty 015).
- **Delimiters:** a line `--BND for details` is no longer a delimiter, so the text after it is shown (stalwart issue 156).
- **Parts:** mail-parser dropped whole parts of malformed multiparts that mime-rs now lists (dovecot-malformed 000).
- **Headers:** `Sub ject:` no longer reads as Subject. A body line no longer reads as `From:` after a `UT` or `Z` zone, and the subject after an `A` zone is no longer lost.
- **Sizes:** they move only where the base64 was prose (RFC 2046's example) or the bytes invalid.
- **Plain view:** the 60 differing views show the same changes, plus decoded sizes and names in place of mail-parser's.

Verified:
- 405 tests pass. The 6 builder tests were ported to read back through mime-rs, the `push_msg_id` test went with its function, and two new tests cover the HTML quote and the flowed unwrap.
- Clippy is clean, and the imap, maildir, gmail+smtp, jmap, pimdir, mbox, m2dir and smtp builds compile without warnings.
- The msgraph-only build keeps its earlier unused-evaluator warnings, `from_mime` now among them.

Spec: commands ("A read message is a designed view" and "Malformed mail reads as its sender meant" modified, the composers' `Date` and `Message-ID` added under "Composers default the From header"); spec/testing/compose-reply-forward.md reworded.
